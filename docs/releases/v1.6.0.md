# Littlepowers 1.6.0 — Project-adaptive delivery

This minor release adds project-level delivery learning without changing
Outcome Lock protocol 1.3, ledger schema 4, model defaults or the single-agent
default. No runtime dependency beyond Python's standard library is added.

## Complete outcomes, lighter execution

- Tasks represent coherent observable results. Edits, commands, tests,
  checkpoints and rollback steps stay inside those results; no fixed task quota,
  mandatory waves or product-scope slicing.
- Planning walks the full user journey, interfaces, existing data and failure
  recovery first. Costly assumptions need project evidence before implementation.
- Tiny understood changes still skip the optional profile and helper. Detailed
  rules are loaded on demand, not injected by hooks or a background observer.

## Adaptive verification and project learning

An optional project profile records boundaries, check definitions, observed costs
and process improvements. The pure helper proposes affected checks and eligible
per-check reuse. Original input snapshots, latest attempts, evidence, environment
and acceptance must remain valid. Unknown impact, newly introduced dependencies,
stale live observations and failed/incomplete runs require fresh checks.
Mandatory tests and existing approval/completion gates remain authoritative.

Project improvements follow **candidate → trial → active → retired**. A trial
predeclares its metric, benefit threshold, quality invariants and stop condition.
Only evidenced benefit can promote it; persisted state must agree with legal
history and promotion evidence. Matching active rules can be applied within
existing authority. Negative/invalid rules fall back to a valid/default strategy,
not a rollback of business code or user data.

The implementation's [verification record](../littlepowers/evidence/2026-10-31-project-adaptive-delivery.md)
covers 346 passing tests, all 11 skill validators, failure injection and the
current Codex self-hosted flow. A real local interpreter-preflight trial preserved
the original failed run, then passed all 30 affected tests without changing code,
assertions, global configuration or licenses.

Three alternating local fixture pairs reduced check executions from 30 to 18
while retaining the same required coverage and known defect detection. The final
fixture's total median was about 186 ms versus 147 ms; cold-run overhead remained.
This is not a model-token, long-term rework or universal host-speed claim.

## Release validation boundary

For this v1.6.0 release, the user explicitly authorized local validation without
enabling the manually disabled GitHub test workflow. The user also authorized
official Codex CLI isolated installation, manifest parsing and exact file
comparison as the substitute for the unavailable standalone Codex plugin
validator. Missing tooling and unrun CI are not reported as passing.

Release checks include the integrated suite, all skill validators, compilation,
Claude strict and Qoder plugin validation, immutable-payload Codex installation
and file-integrity checks. The release audit records their observed results.
No new authenticated Claude Code/Qoder/OpenCode or model matrix is claimed.

Install the exact `v1.6.0` tag and start a new Codex chat to load the new skills.
Do not expect a running chat to hot-load them. GitHub/plugin release only;
no npm publication.
