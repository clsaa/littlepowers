# Littlepowers v0.4 engineering discipline design

**Date:** 2026-07-17

**Status:** Approved for implementation

## Architecture

The new disciplines sit beside execution rather than inside the recovery hook or ledger:

```text
using-littlepowers
       |
       +--> shaping route --> executing-plans
       |                           |
       |                           +--> debugging-systematically (on failure)
       |                           +--> reviewing-changes (risk/request boundary)
       |                           +--> verifying-work (before success claim)
       |
       +--> direct diagnosis ------+--> debugging-systematically

existing read-only hooks + revisioned ledger remain unchanged
```

Codex and Claude Code discover the same skill directories from the repository-root plugin packages. No host-specific fork of the behavior is introduced.

## Skill boundaries

### `debugging-systematically`

This is an entry skill for unexpected technical behavior. It owns diagnosis discipline but not task authorization or completion claims.

Its state machine is conceptual and need not be persisted:

```text
capture symptom -> reproduce -> trace divergence -> test one hypothesis
                                               |              |
                                               |              +--> falsified (count +1)
                                               |                         |
                                               |                         +--> under 3: next hypothesis
                                               |                         +--> at 3: escalate assumptions
                                               +--> supported -> root-cause repair if authorized
                                                                    |
                                                                    +--> original reproducer
                                                                    +--> regression evidence
```

The skill first establishes whether the request authorizes only diagnosis or also implementation. Read-only diagnosis may inspect files, logs, configuration, history, and run non-mutating checks. It does not edit merely because a likely fix is visible.

Each hypothesis is a compact external statement: observed evidence, predicted discriminating result, and smallest safe check. The instruction never asks for private reasoning traces. The failed-hypothesis count applies to implemented or experimentally tested fix hypotheses, not ordinary investigation steps.

### `verifying-work`

This is a completion gate. It owns the relationship between a claim and evidence, not the implementation itself.

The verifier builds a small claim-evidence table:

| Claim | Fresh check | Scope rationale | Observed result |
| --- | --- | --- | --- |
| Changed behavior works | Focused reproducer/test | Covers local rollback unit | Exit/result plus relevant signal |
| Adjacent contract remains valid | Affected integration check when needed | Covers connected boundary | Exit/result plus relevant signal |
| Package/release is ready | Broad release checks when needed | Covers shared/release boundary | Validator/matrix result |

Evidence becomes stale when a relevant file, dependency, configuration, generated artifact, or environment assumption changes after the check. The skill does not require timestamps in the ledger; it compares evidence ordering within the active execution and reruns when uncertain.

The scope classifier considers affected contracts and rollback coupling:

- **Local:** one isolated contract and one independent rollback unit;
- **Connected:** several consumers or a shared boundary whose rollback must be coordinated;
- **Broad:** security, state/schema, hook, packaging, public API, migration, platform, or release surface.

Edit size is only a clue. A one-line manifest change is broad; a multi-line isolated test fixture can remain local. Full-suite execution is reserved for a broad boundary or an aggregate release gate.

### `reviewing-changes`

This is a read-only assessment skill. It may be used by the coordinator as structured self-review or by a host-selected reviewer. It does not create a reviewer or select a model.

The review input contains:

- acceptance criteria or approved outcome;
- exact diff/range and affected interfaces;
- test evidence and known limitations;
- no proposed verdict and no list of suspected findings.

The output contains:

1. acceptance/spec verdict;
2. code-quality verdict;
3. findings ordered by severity, each with location, consequence, evidence, and repair direction;
4. residual risk or unverified assumptions.

The reviewer remains read-only. The coordinator checks each finding against code and requirements, repairs accepted findings, and invalidates/reruns any evidence touched by the repair. This avoids both blind acceptance and performative rejection of review feedback.

## Conditional integration

`executing-plans` gains a compact dispatch table:

| Condition | Discipline |
| --- | --- |
| Failure or unexplained behavior appears | `debugging-systematically` |
| User-requested review, delegated integration, shared milestone, or material rollback cost | `reviewing-changes` |
| Any claim of fixed, complete, passing, ready, or released | `verifying-work` |

The table is conditional. A tiny isolated change still receives diff inspection and fresh focused evidence, but it is not forced through a separate reviewer or full test suite.

`writing-plans` records four items once at plan level:

- global constraints that apply to every task;
- named interfaces or consumers affected by each task;
- feature-level rollback boundary;
- focused, connected, or broad validation commands with rationale.

This improves downstream reviews without creating another planning phase.

## Ledger behavior

No schema change is needed. For a tracked workflow, the coordinator checkpoints concise integrated results and the next action as it does today. Command transcripts and detailed review reports remain in normal tool output or project artifacts only when the repository convention calls for them.

Workers never checkpoint. A worker's test or review report is untrusted input until the coordinator inspects the integrated tree and obtains fresh evidence.

## Packaging

Each new skill is created with the standard skill initializer and contains:

```text
skills/<name>/
├── SKILL.md
└── agents/openai.yaml
```

No scripts or references are needed: each protocol is short enough to keep in one skill file. The plugin manifests already package `./skills/`, so adding directories exposes them to both hosts without a manifest skill list.

Release metadata moves to `0.4.0-alpha.1`. Documentation adds the three disciplines to the capability matrix and model-compatibility explanation without claiming deterministic invocation.

## Validation design

Validation follows the same impact model being introduced:

1. **Per new skill:** run only `quick_validate.py` for that skill and the manifest contract test that discovers skill directories.
2. **Execution/planning integration:** run focused unit tests that assert conditional dispatch, proportional scope, evidence freshness, review verdicts, and rollback wording.
3. **Documentation/version integration:** run manifest/document contract tests and both plugin validators.
4. **Aggregate release boundary:** once all independently reversible features are integrated, run the complete unit/eval suite, all skill validators, Codex validation, Claude strict validation, local install smoke tests, and CI's platform matrix.

Evaluation scenarios cover diagnosis-only authority, three failed hypotheses, local versus broad verification, stale evidence, original bug reproduction, two-verdict review, and the absence of mandatory review/full-suite behavior for tiny edits.

## Rollback design

Use feature-scoped commits:

1. debugging skill, its evals, and focused contract tests;
2. verification skill plus execution/plan integration and focused tests;
3. review skill, its evals, and focused tests;
4. shared docs, version metadata, cache refresh, and release notes.

Reverting one of the first three commits removes one discipline without touching state, hooks, or the other disciplines. The final integration commit can be reverted separately if packaging or documentation causes release trouble. Repository visibility remains unchanged.
