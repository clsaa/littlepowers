# Littlepowers v0.4 engineering discipline specification

**Date:** 2026-07-17

**Status:** Approved for implementation

## Scope

v0.4 adds three host-native, model-neutral skills to the shared Codex and Claude Code package: `debugging-systematically`, `verifying-work`, and `reviewing-changes`. The Unreleased runtime-continuity amendment keeps the read-only hooks and routing model, while extending schema 2 compatibly with bounded observable progress.

## Functional requirements

### Systematic debugging

- Native skill discovery selects the skill for bugs, failing tests, regressions, crashes, performance anomalies, and other unexpected technical behavior.
- Diagnosis requests remain read-only unless the user also authorizes a fix.
- The workflow gathers the exact symptom, reproduction, environment, and recent-change evidence before editing.
- It traces data or control flow to the earliest supported divergence and may compare a working analogue or boundary contract.
- It states one falsifiable hypothesis at a time and runs the smallest experiment that distinguishes it from alternatives.
- A fix targets the root cause, preserves unrelated behavior, reruns the original reproducer, and adds or updates regression coverage when externally observable behavior changes.
- After three failed fix hypotheses, it stops speculative patching and reports the challenged assumption, evidence, and likely architecture-level question.
- It does not impose mandatory TDD, worktrees, commits, subagents, or a particular model or reasoning setting.

### Evidence-gated verification

- Native skill discovery selects the skill before an agent claims that work is complete, fixed, passing, ready, or successfully released.
- Evidence is fresh only when it was collected after the latest relevant code or configuration change.
- Every claim identifies the command or inspection, its scope, exit status or equivalent result, and the relevant observed signal.
- The original reproducer is rerun for a bug fix; absence of the prior failure is not inferred from unrelated tests.
- Delegated worker reports are evidence inputs, not final proof. The coordinator verifies the integrated state before completion.
- The final diff is inspected for unintended files, debug artifacts, accidental generated output, and changes outside the authorized scope.
- Missing tools, credentials, platforms, or flaky checks are reported as limitations or blockers rather than converted into a success claim.

### Proportional test scope

Verification scope follows impact and rollback scope, not edit size alone:

| Scope | Typical change | Required evidence |
| --- | --- | --- |
| Local | One isolated behavior, no shared contract, cheap single-file or feature rollback | Reproducer or focused unit/skill validator plus diff inspection |
| Connected | Several modules or one shared boundary, moderate rollback coordination | Focused checks plus affected integration/build/type checks |
| Broad | State/schema, security, packaging, hooks, cross-platform behavior, public API, migration, or release | Focused checks plus the relevant broad suite or release matrix |

- A full suite is not the default after every small edit.
- A small textual change can still require broad checks if it changes a shared contract, manifest, hook, or release surface.
- The verifier states why the chosen scope covers the plausible rollback boundary.
- When several independently reversible features are combined for a release, each feature gets focused checks first and the aggregate gets one broad release verification after integration.

### Lightweight change review

- Native skill discovery selects review when the user asks, a delegated result is integrated, a milestone changes shared behavior, or the impact/rollback cost is material.
- Tiny isolated changes may use self-review and focused verification without a separate reviewer pass.
- Review is read-only. It does not edit code, mutate the ledger, or silently expand the task.
- When a separate reviewer is available, the task brief presents acceptance criteria, changed scope, and evidence without coaching the reviewer toward approval or listing expected findings.
- Review returns two independent verdicts:
  1. acceptance/spec compliance: `pass`, `fail`, or `blocked`;
  2. code quality: `approve`, `request changes`, or `blocked`.
- Findings include severity, exact file and line when applicable, consequence, supporting evidence, and repair direction.
- Critical and important findings block completion until fixed or explicitly accepted by the authorized user. Minor findings are non-blocking unless they violate an acceptance criterion.
- The coordinator verifies review findings technically, resolves disagreements against the repository and requirements, and reruns evidence affected by any repair.
- Review scope follows the same local, connected, and broad impact levels as verification.

### Execution and planning integration

- `executing-plans` invokes the three disciplines by condition rather than for every task.
- `writing-plans` records global constraints, task interfaces, rollback boundaries, and proportional validation commands so implementation does not rediscover them.
- The root coordinator remains the only ledger writer. New skills use existing checkpoints and do not add ledger fields.
- Full-workflow completion still requires `phase=verify` and fresh evidence.

### Runtime continuity amendment

- If a loaded plugin path disappears, execution and ledger mutation stop until exactly one enabled Littlepowers installation is resolved through the host's JSON plugin listing, its manifest is verified, current skills are reread, and context is reloaded.
- A plugin replacement is not hot-loaded into a running task. Installation guidance uses a new task/session boundary and reports ambiguity instead of guessing a cache path.
- A full-route brainstorm checkpoint points to a shaping artifact in the resolved brainstorm area. An ADR may accompany it but does not replace it; legacy references remain readable and are not silently migrated.
- Ledger schema 2 accepts optional `progress` bounded to 800 characters. Missing progress normalizes to `null`, schema 1 still migrates deterministically, and the prior schema 2 implementation can ignore the added field.
- Progress names an observable milestone or acceptance-check count. It is rendered in status and Hook context; guessed percentages are forbidden.
- Execution writes a continuity checkpoint before likely compaction, handoff, plugin replacement, or after a long batch crosses multiple subsystem boundaries. This does not require a broad test run at each checkpoint.

### Packaging and compatibility

- All three skills contain only `name` and `description` frontmatter and include Codex UI metadata.
- The same skill files ship in both Codex and Claude Code plugin packages.
- No skill selects or overrides GPT-5.6 Sol, Codex Ultra, Claude Fable 5, Claude Opus 4.8, reasoning effort, or subagent count.
- Instructions require observable summaries and evidence, not hidden chain-of-thought disclosure.
- Codex and Claude plugin manifests share version `0.4.0-alpha.1`.

## Non-goals

- Guaranteeing that a host model invokes a skill at every applicable moment.
- Replacing host-native code review, task delegation, or CI.
- Treating test count as proof of correctness.
- Running all tests after every edit.
- Automatically reverting, committing, pushing, publishing, or changing repository visibility.

## Acceptance criteria

- A debugging scenario does not edit during diagnosis-only authority and does not propose a fix before reproduction/evidence.
- Three failed hypotheses produce an escalation rather than a fourth speculative patch.
- A small isolated skill edit selects focused validation and explicitly declines an unnecessary full suite.
- A manifest, hook, schema, security, cross-platform, or release change selects affected broad verification.
- A completion report cannot pass using evidence collected before the latest relevant edit.
- A bug-fix completion report includes the original reproducer and regression evidence.
- A review report is read-only, contains both verdicts, and gives actionable location/evidence for findings.
- Tiny local work can finish without forced subagent review when focused checks and self-review are sufficient.
- Cache replacement recovery rereads the current plugin before execution, ADRs remain companion records, and status interruption resumes from persisted evidence-based progress.
- Every new or changed skill passes the skill validator; manifest, Codex plugin, Claude strict plugin, unit, eval, and release checks pass at the aggregate boundary.
- Feature changes are committed in independent rollback units before the shared release integration commit.
