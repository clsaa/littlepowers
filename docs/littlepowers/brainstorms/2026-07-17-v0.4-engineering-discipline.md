# Littlepowers v0.4 engineering discipline brainstorm

**Date:** 2026-07-17

**Status:** Selected direction

## Outcome

Add three opt-in engineering disciplines to Littlepowers: root-cause debugging, evidence-gated completion, and lightweight change review. They must work in both Codex and Claude Code, remain model-neutral, and scale their verification and rollback boundaries to the actual impact of a change.

## Problems to solve

1. A coding agent can jump from a symptom to speculative edits without first reproducing or tracing the failure.
2. A completion claim can be based on stale, partial, or worker-reported evidence rather than a fresh check of the changed behavior.
3. Review can be omitted for consequential changes or expanded into expensive ceremony for tiny local edits.
4. Running the entire test suite after every small edit wastes time and obscures which evidence actually validates the change.
5. A broad mixed commit makes it hard to reverse one capability without discarding the others.

## Options

### A. Copy the full Superpowers development workflow

Adopt mandatory debugging, TDD, subagent review, worktrees, and commits for every task.

This provides a complete methodology, but it would duplicate host orchestration, add static prompt weight, and conflict with Littlepowers' proportional-routing goal. It also makes small work unnecessarily expensive.

### B. Add advice only to the existing execution skill

Put a few debugging, verification, and review bullets into `executing-plans`.

This is small, but the three behaviors would be hard for native skill discovery to select independently. Their trigger conditions and evidence contracts would also be too easy to blur together.

### C. Add three focused skills with one integration contract

Create independently discoverable skills for systematic debugging, verification before completion, and reviewing changes. Integrate them through `executing-plans`, use the existing ledger only for tracked workflow checkpoints, and add no new hook or state schema.

This preserves native discovery in Codex and Claude Code while keeping the static recovery protocol small.

## Selected direction

Choose option C.

### Systematic debugging

- Reproduce and collect evidence before proposing a fix.
- Trace the failing value or boundary and compare against a working reference where useful.
- Test one explicit hypothesis with the smallest discriminating experiment.
- Fix the root cause, rerun the original failure, and add regression coverage when behavior changed.
- After three failed fix hypotheses, stop patching and surface an architectural or assumption-level question.
- Preserve the distinction between diagnosis-only authority and permission to change code.

### Evidence-gated completion

- Require fresh evidence for every success claim.
- Match checks to the rollback and impact scope: a local reversible change gets focused checks; shared contracts, packaging, platform behavior, or a release get broader integration checks.
- Record the command, exit status, and relevant observed signal rather than reporting only “tests pass.”
- Treat worker reports as inputs; the coordinator verifies integrated results.
- Inspect the final diff for unintended files, debug artifacts, and scope expansion.

### Lightweight change review

- Review when the user requests it, a delegated result is integrated, a milestone changes shared behavior, or rollback cost is material.
- Do not require a separate review ceremony for every tiny, isolated edit.
- Keep the reviewer read-only and independent of implementation framing.
- Return two verdicts: acceptance/spec compliance and code quality.
- Report actionable findings with severity, location, consequence, and repair direction; the coordinator adjudicates them against evidence.

## Rollback and test boundaries

Implementation is divided into feature-scoped commits and file groups:

1. systematic debugging skill and its focused tests;
2. evidence gate and execution integration with focused tests;
3. review skill and its focused tests;
4. shared documentation, metadata, installation refresh, and release validation.

Each feature runs only its validators and affected contract tests while being built. The full cross-platform/release matrix runs once after the aggregate plugin surface is complete because the release changes skill discovery, documentation, and both plugin packages.

## Non-goals

- Mandatory TDD for every change.
- Automatic subagent creation, model selection, reasoning-effort selection, worktree creation, commits, pushes, or releases.
- A second review orchestration engine.
- New ledger fields or hooks when existing checkpoints can carry the needed evidence summary.
- Claims that a plugin can force GPT-5.6 Sol, Codex Ultra, Claude Fable 5, or Claude Opus 4.8 to follow instructions.
