**No scope delta。** 四个方向在一个工作流、一个完成标准中全部实现；下文任务只是连续实施顺序，不是分期产品或可单独宣布交付的子集。

采用 Compact：一份文档承载需求、设计、实施和验收。选择可撤销、按需加载的项目策略扩展，不改变 schema 4/protocol 1.3、审批、契约、完成门禁或宿主权限模型，因此不引入新的状态迁移和跨宿主调度架构。若实现前发现必须改变这些边界，返回本方案审阅，而非隐式扩大方案。

## 3. 先整体考虑，再确定实施顺序

每次非平凡规划先在现有 brainstorm/shape/plan 内回答一组适用问题，不另建必填文档：

1. 用户从哪里进入，经过什么状态变化，最终真正得到什么结果？
2. 哪些模块、调用方、接口、数据所有者及历史数据受到影响？
3. 正常路径、最重要的失败/恢复路径、兼容与发布回滚是否连贯？
4. 当前工具、权限、测试环境与数据能否证明上述结果？
5. 哪些事实已验证，哪些假设会改变方案，哪些相关教训已过期？

只检查与当前目标相关的文件和已声明边界，不全仓通读或遍历历史会话。关键假设优先用最小授权探查验证；未解决的重大产品/架构/安全选择按现有路线升级或询问，不能只填“0 open questions”。

任务聚合规则：一个完整用户流程可覆盖多个 OUT；读文件、改单个函数、加测试、更新状态属于内部操作。独立用户成果或真实的依赖协调需要才创建一级任务。小提交、回滚边界、恢复检查点保留在任务内部；没有固定任务数量配额，也不声称纯规则能机器判定所有语义切片。

## 4. 一条端到端路径与三个组件

`当前目标 + 项目现状 + 有效项目经验 → 整体方案 → 检查建议 → 执行/验收 → 有证据的项目经验更新`

### 4.1 项目交付档案

默认位置建议为项目自己的 `docs/littlepowers/project-delivery.md`，允许项目指令指定其他明确路径。它不是 Littlepowers 全局配置，也不是父验收标准。读取按需；没有档案时继续现有流程，不要求先填表。

首次有意义且允许写文件的实施任务，可从当前已验证的仓库命令、模块边界、适用终端和环境创建简短档案；只读诊断不创建或更新。已有文档优先引用，不复制整个架构文档。

一个文档包含短说明和 `littlepowers:delivery-profile:v1` 数据块：

- 身份/版本：`profile_version`、`project_id`、`revision`；当前流程固定采用的档案摘要。
- 边界：模块/接口/数据归属和显式消费者关系，未知关系明确标记。
- 检查目录：稳定 check ID、所支持的行为/边界、命令或操作说明、适用终端、前提、触发条件、输入范围、不可省略的要求来源。
- 观察：检查实测耗时、失败类别、环境限制、返工原因和来源证据；耗时未知不写成零。
- 经验：适用条件、证据引用、建议、失效条件、已验证/待验证状态；不保存原始会话、秘密或个人数据。

按检查组而非每个测试用例建目录，最多 128 组、64 条经验；辅助调用输入总计不超过 2 MiB。超限明确报错或缩小所提交范围，不能静默截断必需检查。只保留小规模近期耗时样本和摘要，原始失败证据留在原验收产物中。

更新发生在规划边界、重大返工/环境变化、验收结束，有新事实才写。当前工作流的检查标准不能被中途更新的经验替换。并行 worktree 使用各自的版本和工作流证据，不共享可变缓存；合并遵循现有 Git 流程。写前比对所读版本，发现变化先重读协调。

### 4.2 无副作用的检查与复用建议器

新增 `scripts/littlepowers_delivery.py`，Python 标准库实现；stdin 输入、stdout 输出的有界 JSON 协议。不执行命令、不写档案/账本、不访问网络、不发现项目、不启动 Agent。

操作为 `select`、`reuse`、`learn`：输入仅为协调者显式提供的档案、当前变更/要求/能力、检查回执和当前指纹；返回建议与逐项原因。宿主工具仍由根协调者调用。文档中的命令和历史观察一律视为数据，不直接执行。

选择顺序固定为：

1. 保留当前需求、仓库指令和发布约束规定的必需检查；费用不能取消它们。
2. 覆盖原问题、已知变更边界及显式消费者，增加适用的历史数据/用户流程检查。
3. 依赖、变更清单或覆盖关系不完整时输出 `unknown/blocked`，建议能重新建立结论的最小边界检查；不能把“没列出”当“没影响”。
4. 仅在已知适用关系和有效回执下提出复用；不适用也必须有依据。
5. 在已覆盖风险的候选集合内，优先便宜、确定、能早发现问题的检查，并合并同一共享检查的重复执行。
6. 输出 `run`、`reuse_candidates`、`not_applicable`、`blocked`、覆盖缺口、原因和可用的历史成本估计。协调者确认范围完整性后执行，辅助结果本身不是通过或豁免。

成本预算是调整顺序、准备工作和执行方式的信号，不是通过门槛。慢检查可提议复用构建/数据准备、使用已有选择器、隔离不稳定外部服务或改善测试基础设施；改变项目测试设施需要在当前实现授权内，超出时另行提出。不能自动删测试、改变必需 CI、隔离失败测试或把 flaky 记为 pass。并行仅在已有工具、资源隔离和权限允许时使用，不因此启动子 Agent。

### 4.3 逐检查证据与受控反馈

在现有证据产物旁保存有界回执，不增加第二个工作流账本。建议器接受显式传入的回执；可选本地索引位于已忽略的 `.littlepowers/delivery/<workflow>/`，不存在时不影响普通执行。

回执最少包括：check ID、尝试 ID、所支持 OUT/行为、命令/操作及版本、检查前输入快照、相关配置/依赖/数据/环境/权限标识、运行结果/退出码/耗时、证据路径及摘要、前一次失败或被替代回执的引用。运行中、超时、失败和未知不能成为成功缓存。

复用需要检查定义、验收要求、相关输入、数据和环境均可证明连续，原证据仍可读且未变。动态服务事实还必须符合该检查自己的新鲜度规则；没有规则则重新观察。新增/删除/重命名文件、消费者或测试必须纳入变更判断，不能仅比较旧回执里已有的文件。

辅助程序不扫描或认证这些外部事实；由协调者使用已有安全输入捕获/读取接口提供观察值。未知、未声明、顺序不明或缺失证据均不复用。复用候选不能直接获得 `complete` 权限。

保留旧回执，将新运行和有效复用结果汇总成新的 Verification Record。`inputs` 是各有效检查原始输入快照的一致并集：同一路径不同摘要必须重新验证受影响检查；不得在最终汇总时重新采集当前 hash 冒充旧检查输入。原有 256 路径/安全路径限制仍有效，超出范围明确暴露限制，不另造摘要绕过门禁。Plan/Contract 变化继续服从原有审批与失效机制。

`learn` 只输出附有证据与适用范围的档案修改建议。协调者可以在已授权的项目工作内自动保存事实、优化等价检查的顺序和重复准备工作；改变需求、验收标准、必需检查、权限、审批或不可逆操作必须走原审批。旧经验是提示，不是上级指令；来源缺失、版本/环境不符或与当前要求矛盾时停止应用。单次观察不宣称普遍规律，负收益也记录。

### 4.4 自迭代的生效与退回闭环

自迭代的对象是当前项目的交付方法，覆盖任务组织、整体规划/设计、实现中的协作与准备、测试、验收和中断恢复，不限于测试选取。它不是模型训练，也不是自动修改、安装或发布全局 Littlepowers。

由当前 Agent 在正常工作中观察问题、分析原因、提出并执行调整；纯建议器检查声明的版本、作用域、证据和转换前提，再提出下一状态。根协调者核对真实观察后落盘。程序不能从自然语言证明“设计一定周全”，也不能认证调用者提交的事实；语义判断仍需实际产物和验收证据。

在同一项目档案的经验记录内增加轻量状态，不新建后台服务、账本或人工审批阶段：

| 状态 | 进入条件与允许行为 |
| --- | --- |
| `candidate` 候选 | 有明确问题、来源证据、适用条件和可验证的改进假设；保存候选，不作为默认规则应用。证据不足时保留未知，不制造经验。 |
| `trial` 试用 | 当前任务确实适用；改动在已授权范围内、可逆、不会改变必需验收/权限；先声明对照策略、成功指标、不可退化项和停止条件，再随正常工作试用。 |
| `active` 生效 | 有真实试用结果，预先声明的收益条件满足，必需覆盖和相关缺陷检出未退化，适用范围与证据仍有效；后续匹配任务可自动采用，不逐次要求人工批准。 |
| `retired` 停用 | 试用失败、负收益、证据/环境/要求失效或出现相反证据；立即停止自动应用，保留原因和历史，不覆盖原失败。重新尝试需要新候选版本和新依据。 |

每条改进在原有经验字段外记录：稳定 `improvement_id`、版本、类别、状态、问题与假设、实际策略差异、对照/退回策略、适用与失效条件、试用指标/不可退化项、来源及运行回执、结论和状态变化原因。指标可为重复操作次数、准备/等待/检查总耗时、遗漏边界是否在编码前被发现等；未测量的指标保持 unknown。

`candidate → trial → active` 不能跳过试用证据；缺少收益或安全性证据时不晋升。试用次数不是通用置信度门槛：一次验证可支持一次确定环境事实，不能据此宣称长期返工率或所有模型/宿主的收益。需要重复对照才能成立的结论，在样本足够前保持候选或试用状态。

对 `active` 的适用性检查发生在下一次相关正常边界，不依赖计时唤醒。条件不匹配时不应用；证据已失效时停用。退回到最后一个仍满足当前要求的已知策略；没有有效历史策略时回到现有保守验证方法，而非恢复同样过期的旧规则。退回对象仅为执行策略，不自动回滚业务代码、数据库或外部操作。

自动执行范围内的等价调整由协调者直接试用/应用；删减必需检查、降低标准、改变需求/审批/权限、改 CI 或超出任务范围的测试设施改造仍需正常授权。产品代码或数据的撤销需要对应授权，不能借“自动回退”扩大权限。

仅在既定正常边界且有新观察时处理候选；同一边界最多引入一个新的策略变量，避免无法归因的多项同时试验。优先利用本来就要运行的检查，不为每条经验额外双跑全量测试。没有合适场景时保留候选，不阻塞已符合要求的产品交付；辅助器不可用时不应用新建议，继续当前安全流程。

状态转换使用显式版本和当前策略摘要作为前提，输出候选更新及理由；根协调者发现版本冲突先重读协调，不重复应用或覆盖他人经验。状态和试用回执随项目恢复；中断、未知结果、过期审批、失败检查不能被转换成生效。

例：若一次接口修改漏考虑旧数据，先记录适用的接口/数据边界和遗漏证据；在下次相同边界的正常规划中试用提前检查旧格式；确认其确实在编码前发现了相关问题且未损害原验收后，保存为该边界的生效经验。接口或数据模型变化使这条经验失效时重新验证，不能无条件扩展为所有任务的额外步骤。

### T2 — 验证完整用户流程与实际收益，修正集成问题

| AD-07 失败修复与恢复 | 保留失败尝试；失败/超时/运行中不复用；新证据替代旧结果；中断后不重复提交已确认完成的操作。 |
| AD-08 成本超预算及规则冲突 | 必需检查保留；慢/不稳定不是 pass；档案不能推翻当前请求、仓库规则、审批和完成门禁。 |

| AD-11 四宿主与旧工作流 | 旧账本/技能路径保持兼容；新机制不依赖某宿主私有工具、不修改模型设置；能力缺失明确降级。 |
| AD-12 收益与漏检对照 | 相同需求、候选、数据与缺陷集下，必需覆盖和缺陷检出不减少；成本包含档案准备、辅助器、运行和恢复，负收益如实记录。至少演练一个规划/设计改进和一个测试/验收改进的生效及退回过程，不能只证明测试选择器有效。 |
